## Findings

### B1 [medium] - Receipt replay unnecessarily takes writer locks

- Category: LOGIC_BUG
- Location: crates/monica-core/src/imports.rs:135-136
- Confirmation selector: B1

Description: Every receive call performs INSERT ON CONFLICT DO UPDATE of the same idempotency_key before checking the saved body hash. A retry of an already committed receipt therefore requests a conflicting row-writer/key lock despite changing no identity or business fact. Legitimate processing/FK readers can hold that row. With the application's one-second interactive lock limit, the signed API maps the resulting lock timeout to409, incorrectly presenting an unchanged, previously accepted batch as conflicting.

Rationale: This branch introduces the Rust receiver and mutable batch-progress row. Its no-op UPSERT couples immutable receipt identity to mutable processing locks. Existing committed receipts should be read/reused while preserving strict body-hash checks. A genuinely concurrent first acceptance still needs atomic unique-key arbitration and atomic input/progress creation.

Evidence:

- core imports.rs135-136 explicitly uses ON CONFLICT(idempotency_key) DO UPDATE SET idempotency_key=excluded.idempotency_key.
- The HTTP caller verifies HMAC/nonce and computes the raw SHA-256, then calls receive in the same transaction. Its failed(error) mapping returns409 for this database error.
- Actual NAS sourcec2 accepted batchnas-crash-durable-fixture, survived server plus PostgreSQL SIGKILL, projected all1000 records and reached statuscomplete/processed_count1000. Retrying the same generated body returned409 with detail Import conflicts with a saved identity or checkpoint.
- Captured server logmonica-rs-final-38d8f4d6-server.log at2026-11-13T13:01:51.205033Z reports import rejected: canceling statement due to lock timeout. The preceding statement is this no-op import_batches UPSERT and took1.001624seconds.
- Independent retained-fixture reproduction confirmed the exact original raw request hash ebcc6a18fdbd4c028fcbfeed1ea1f1894549b3cc9d7d84afdcad48bddcb69841 and1000 durable messages. Holding FOR KEY SHARE caused the old UPSERT to hit the configured250ms diagnostic lock timeout after0.270004seconds; an ordinary identity/hash SELECT completed in0.000788seconds while the holder remained active.
- Holding an in-flight progress UPDATE reproduced the same failure after0.253809seconds; reading the committed identity/hash still completed in0.000789seconds. Both holders were rolled back. This distinguishes the lock defect from the separately measured slow NAS fsync/transport-bound problem.
