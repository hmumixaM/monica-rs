## Findings

### B1 medium - Status failure skips cancellation cleanup

- Category: LOGIC_BUG
- Location: `.local-validation/nas-migration-20261113/nas-restore-converted-worker.py:69-70`
- Confirmation selector: B1

Description: The new `finally` block calls `status('database_restore_cancelling', ...)` before `stop_restore(process)`. `status()` performs several fallible filesystem operations and flushes stdout without handling errors. If any of these fails after the restore starts—for example, an `OSError` from a full destination volume while the restore/log is growing—the exception leaves `finally` before cleanup runs. The live Docker exec and PostgreSQL restore can therefore continue without this worker's memory/stop supervision. This defeats the same resource/cancellation guarantee that the repair is intended to establish, although commands still directly target the new isolated database.

Rationale: This is an introduced production control-flow defect in the repair's cleanup path. The script explicitly converts monitor exceptions into cancellation at lines 65-66 and adds owned cleanup at lines 67-70, but makes that cleanup conditional on a successful status write. File-descriptor closure while unwinding the worker is not termination or reaping of the already spawned Docker exec. The prepared launcher retains the supervisor after SSH disconnect, but does not supervise or repair a worker that exits at this point.

Evidence:

- Line 8: `status()` calls `write_text`, `chmod`, `replace` and flushed `print`; all can propagate I/O exceptions.
- Lines 54-56: the restore child has already been started with inherited artifact/log descriptors before this path is reached.
- Lines 68-70: an exception at line 69 exits the `finally` suite before line 70.
- Exact-source pure-memory execution supplied valid artifact/hash, target identity, zero initial tables/clients and low available memory, then injected `OSError('synthetic ENOSPC')` into only the cancelling status write. Observed: phases `[database_restoring]`, termination queries `0`, child return code `None`, no wait/reap call, and worker exit through that `OSError`. No NAS access, real processes, real database, or test artifacts were involved.
- Supporting launcher lines 22-25 use a dedicated log and `start_new_session=True`, so SSH disconnect protection is present, but no external worker-exit cleanup is added there.

Proposed correction: Ensure `stop_restore(process)` executes even when cancellation status publication fails, for example with a small `try/finally` around the status call or by making status publication best effort within the cleanup branch. Preserve cleanup ownership until the child exits and the tagged backend is absent. Re-review the resulting latest source in another fresh context before execution. This review does not edit the worker.
