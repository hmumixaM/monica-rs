### B1 medium - String message payload aborts Chatlog reconciliation

- Category: `LOGIC_BUG`
- Location: [scripts/legacy-chatlog-import.py:210](/Users/maxhu/play/monica-rs/scripts/legacy-chatlog-import.py:210)
- Confirmation selector: `B1`

Description: The reconciliation path assumes every existing CRM message content object is a JSON object and calls `payload.get(...)` unconditionally. The CRM import explicitly accepts and preserves JSON string payloads. When the frozen Chatlog snapshot contains that same valid message, conversion raises `AttributeError: 'str' object has no attribute 'get'` before applying or marking the page. Every retry encounters the same record, so the Chatlog migration cannot finish.

Rationale: This is introduced in the new importer. It is not blocked by a compiler/linter or by the source schema: `payload_json` is jsonb, and the new CRM converter deliberately handles a string at legacy-import.py:458. Normalizing a string to its text for comparison, while preserving its original content object, avoids the crash.

Evidence:

- legacy-import.py:455-466 preserves the content object's original representation and installs message evidence; line 458 handles str, dict and other JSON values.
- legacy-chatlog-import.py:192 retrieves that immutable `c.payload_json`; line 210 calls `.get` before checking the payload type.
- Independent in-memory extension of `scripts/test-legacy-import.py::MigrationContract` changed the synthetic source content to `Jsonb("Original string body")`, successfully ran the CRM importer and the actual offline finalizer, then reconciled source record `server:7` in the same conversation/time. It reproduced exactly `'str' object has no attribute 'get'`.
- The probe used the fixture's self-created temporary PG cluster and synthetic account/data only; it was not persisted into source.

### B2 medium - Unclassified Chatlog tables pass conversion

- Category: `BUGBOT_RULES`
- Location: [scripts/legacy-chatlog-import.py:45-46](/Users/maxhu/play/monica-rs/scripts/legacy-chatlog-import.py:45)
- Confirmation selector: `B2`

Description: Chatlog inspection records SQLite table names without assigning any conversion/archive/rebuild disposition or rejecting unknown tables. The reused Reader processes only `contact`, `Msg_<md5>` and `SnsTimeLine`; all other tables and entirely undiscovered DB paths are omitted from business conversion. Its files nevertheless become done, satisfying the new importer's completion check and allowing status `converted`. A future or unexpected business table can therefore be silently omitted while conversion appears complete.

Rationale: The user's explicit rule requires every source table to be classified, and docs/NAS_ISOLATED_DEPLOYMENT.md says unclassified tables stop conversion/acceptance. The four-PG inspector enforces this at legacy-import.py:136-139, but the new Chatlog inspector does not. Retaining a raw SQLite file protects bytes; it does not classify or account for its business tables. This finding asks for explicit classification, including intentional archival dispositions, rather than automatic conversion of every system/support table.

Evidence:

- New inspect at lines 38-46 collects `tables` only; there is no mode/count/disposition validation.
- Existing collector-chatlog.py:234 restricts the processed table list; lines 236-238 advance past unsupported tables, and lines 284-289 can mark the file done.
- New legacy-chatlog-import.py:369 checks only Reader file completion, then lines 373-377 settle and mark converted.
- Independent temporary SQLite probe created contact.db with one supported contact and one row in `unknown_business_messages`. `inspect` accepted `['contact', 'unknown_business_messages']`. A full Reader pass emitted one contact record and ended with `SELECT count(*) FROM files WHERE done=0 = 0`; the unknown table received no disposition or reconciliation.
- The same inspect also lists arbitrary *.db files even though Reader.discover only recognizes fixed contact/message/sns paths. One shared classification frontier covers both cases.
