## Findings

### B1 medium - Receipts prevent reconciliation after semantics change

- Category: `LOGIC_BUG`
- Location: [scripts/legacy-chatlog-import.py:357-360](/Users/maxhu/play/monica-rs/scripts/legacy-chatlog-import.py:357)
- Confirmation selector: `B1`

Description: `Importer.page` returns immediately whenever a snapshot/page digest already has a receipt. The Reader also emits only source records whose source hash changed. Neither identity includes the reconciliation algorithm/version, and there is no force-reconciliation entry point. Consequently a snapshot applied under the earlier sender-comparison implementation cannot be repaired by ordinary `apply` after the comparison is corrected. Reusing the original Reader state emits nothing; even a completely new Reader state emits the same page digests and the SQL receipt short-circuits the new comparison. `verify` correctly rejects the stale sender, but retries cannot correct it. The migration remains blocked or can be marked converted again with the wrong attribution until all data is rebuilt or a private bypass is used.

Rationale: The full feature is new in this dirty diff. The same change set added durable receipts and the now-correct sender comparison at lines 264-269, but the receipt contract prevents the current implementation from visiting already-receipted rows to close that repair. The parent additionally reports a real restored-copy verification failure after the sender fix. This report does not rely on access to those real copies: the reviewer independently reproduced the skipped correction on disposable synthetic data.

Evidence:

- `scripts/legacy-chatlog-import.py:64` derives the snapshot ID solely from the manifest; `:358-360` checks only snapshot ID and page digest, then returns without checking target content/attribution.
- `scripts/collector-chatlog.py:174` skips a completed unchanged source file; `:274-280` emits only changed source hashes. A new state still gets a cycle derived from the same source file stamp (`:194`) and a digest with no reconciliation version (`:303`).
- `scripts/legacy-chatlog-import.py:264-269` now compares authoritative sender fields, and `:272` rejects differences in verification. That code is unreachable during ordinary replay of a receipted page.
- Independent disposable probe extended the existing test harness in memory, ran its complete two-snapshot contract, restored its deliberate final content tampering, then modeled an earlier stale sender projection for source record `server:8`. It used a brand new Reader state and the same frozen source. Three source pages were emitted during apply, yet all receipts short-circuited reconciliation; the sender remained `synthetic-old-attribution`. An independent verification scan raised `Chatlog message content or attribution differs`.
- The probe's first variant used the fixture's deliberately absent sender reference; verification correctly preserved that source gap. The successful reproduction instead used an authoritative nonempty source sender. This distinction confirms the issue is receipt bypass, not the intentional retain-existing-attribution policy.

Proposed repair: add an explicit, guarded reconciliation/recompute operation for an unchanged frozen manifest. It must scan from clean Reader state and bypass old receipts for that declared reconciliation version or operation, execute existing `messages`/`correct`/`queue` semantics, preserve immutable original content and revision history, settle deterministic projections, then run independent read-only verification. Merely changing Reader state or deleting `known` rows is insufficient. Avoid arbitrary direct sender updates, which would bypass provenance and source-gap rules. Add a regression that first stores the earlier stale attribution plus a valid receipt, runs the supported recovery operation, and verifies the same original message ID/content object and a new correct version.
