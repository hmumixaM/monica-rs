# Pinned compatibility evidence

Current platform execution is recorded in the [2026-11-13 final acceptance](../reviews/2026-11-13-platform-acceptance.md). The chronological status notes below describe the original contract-freeze checkpoints. Current registration covers166 operations; the148-operation smoke snapshot remains historical and does not certify every operation/input behavior.

The golden files are generated by executing selected **original pure function
definitions** from `git show` at the two accepted commits. The generator reads no
working-tree files, credentials, exports, or runtime directories from either
original checkout. All inputs are generated synthetic values.

Run with Python 3.11 or newer:

```sh
python3 scripts/legacy-contract.py --check
cargo test --locked -p monica-core --test identity
```

Each baseline contains 162 canonical/hash cases, five raw JSON numeric parsing
cases and 48 account/object identity cases, plus invalid account cases. Coverage includes provider/account/kind
isolation, whitespace preservation in nonblank IDs, Unicode and combining
characters, NUL removal in keys and values, colliding sanitized keys in both
orders, raw string versus JSON hashing, signed zero, float exponent formatting,
subnormal/max finite floats, arbitrary-size integers and 128 seeded finite binary64 samples. Source
paths, commits, and full source-file SHA-256 values accompany the vectors.

`*-dates.json` also freezes 20 exact/partial date normalization cases by
executing the original pure date functions at a fixed synthetic "today". Rust
server tests compare normalized values and rejection codes against both pinned
baselines, including leap days, unknown years, future birthdays and labels.

`canonical_utf8` and `observation_sha256` come from `canonical_json` and its
SHA-256. `content_sha256` comes from the original `content_hash`, which hashes a
string's raw UTF-8 bytes. For example, its addresses for the string `"0"` and
number `0` coincide. Callers must not silently substitute this legacy CRM
primitive for source observation hashing or typed content addressing. The
baseline content store handles typed collisions separately; that storage port
is still part of the domain work.

`*-declarations.json` is an AST audit of **declarations**, with source hashes and
line numbers. There are 143 CRM declarations and 148 desktop declarations. Five
desktop pipeline/CDC operations were missing from the initial route ledger and
are now explicitly pending there. A declaration does not prove registration;
runtime capture must check the actual operation union. The summary/retirement
routers, for example, are included at the end of each pinned main module, after
the initial router list.

## Runtime capture at the original freeze

`legacy-contract.py --runtime` stages only pinned `services/api/app/*.py` and SQL
source files into a fresh temporary directory. A subprocess imports the real
FastAPI app with database connections and outbound socket connections denied,
fresh synthetic settings, AI disabled, and no inherited application environment.
It does not start the app lifespan, workers, collectors, or migrations. The mode
captures the real `app.openapi()` and six health/CSRF/validation HTTP fixtures
using the real middleware and routing. For validation cases only, authentication
and DB dependencies are overridden; business reads/writes are not simulated.
The resulting HTTP manifest records dependency versions, source provenance and
the runtime/ledger route differences.

The supervising parent created separate Python 3.12 environments with each
baseline's `uv.lock`, regenerated both actual OpenAPI documents and synthetic
HTTP fixtures, and ran runtime capture/check successfully. The executor repeated
both checks using those environments. Critical versions match the locks:
FastAPI 0.141.1, Pydantic 2.13.5, Starlette 1.6.0, SQLAlchemy 2.0.54 and HTTPX
0.28.1. The earlier environment installed dependency ranges (FastAPI 0.162.4);
the added lock-version check rejected it, and those provisional captures have
been replaced. Broader synthetic business request/response fixtures and actual
differential Rust HTTP tests remain part of API implementation acceptance. The
executor sandbox cannot install dependencies itself (DNS unavailable; `uv`
additionally panicked on macOS system configuration), so the parent performed
that isolated setup.

For the supervising parent, create a temporary dependency project from the

## Rust wiring and original validation checkpoints

Source ingestion now uses the platform UUID namespace, account-local kind/object
UUIDs and canonical source observation hashes. `Record.kind` defaults to `record`
for the development CLI; source adapters must pass their real object kind.
Migration `0006_object_kinds.sql` changes the uniqueness key to
`(account_id, object_kind, external_id)`. Profile fields now use the actual legacy
public address: raw UTF-8 for strings and canonical JSON for other values.
`0027_content_objects.sql` and `monica_core::content::register` atomically reuse
immutable content, selecting the legacy `json\0` canonical fallback only if the
unprefixed address is already occupied by a different typed value. Field writes
sanitize NULs before storing the value. No-op detection compares canonical typed
values so PostgreSQL numeric formatting cannot manufacture another revision.

The baseline Rust development scheme used different UUIDs. These changes are for
fresh isolated test databases. They do not rekey existing observations or jobs
and are not an existing-data migration or production cutover. Full source/CRM
schema and typed-content-store compatibility remains unfinished. The tested JSON
integer domain includes arbitrary Python-size integers. Fractional literals are
rounded to binary64 before both hashing and persistence, matching Python JSON
parsing. Nonfinite numeric extensions/overflow are rejected before persistence.
